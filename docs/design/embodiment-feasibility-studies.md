# Embodiment Feasibility Studies

## Decision

Mujica must reject cheap, visible embodiment defects before it spends
Controller or RL budget. A static rendering is useful for forming a hypothesis,
but the next step must be a reproducible probe over the exact compiled plant.

Two commands form that pre-training boundary:

```text
mujica design analyze <project> --assembly ID [--samples N] [--json]
mujica design study <project> --study ID [--json]
```

`design analyze` runs a deterministic low-discrepancy sweep of bounded actuated
joint workspace against four frozen resting orientations. It reports authored
home support, per-foot surface clearance, simultaneous collision-free foot
contact opportunities, second-foot gap, non-foot support, self-collision,
centre of mass, support margin, and gravity-bias actuator utilization. It also
renders the best collision-free sample for each orientation.

The output is content-addressed under ignored
`.mujica/design-analyses/design-analysis-<hash>/` and contains:

- `analysis.json` for Coding Agents;
- `report.md` for review and diffs;
- `index.html` plus four local PNGs for visual inspection;
- a manifest binding the compiled Assembly/model, Runtime/MuJoCo source,
  settings, and every generated byte.

## Falsifiable candidate families

A checked-in `design-studies/<id>.design-study.json` names one baseline and one
or more candidates. Each candidate states:

- the exact Assembly;
- the physical hypothesis;
- the prose falsification condition;
- a minimum authored-home contact count;
- a minimum collision-free foot-contact count for each frozen orientation.

All candidates use the same declared sample budget and analyzer settings.
`design study` evaluates every Assembly, applies the authored thresholds, and
generates one ignored local comparison artifact:

```text
<project>/.mujica/design-studies/design-study-<hash>/
  result.json
  report.md
  index.html
  manifest.json
```

The HTML page references the integrity-checked local Design Analysis images.
It is deliberately a generated projection, not browser-owned robot source.
Clone plus command execution rebuilds the complete page; no image asset belongs
in Git.

## Interpretation

The probe is a screen, not a solver:

- a failed expectation falsifies the authored hypothesis within the exact
  sample budget;
- a passing expectation only establishes sampled kinematic contact
  opportunity;
- sampling failure is not mathematical proof of impossibility;
- contact opportunity is not dynamically reachable self-righting;
- gravity-bias effort is not a contact-force or trajectory optimization;
- MuJoCo output is not physical evidence.

Accordingly, `SUPPORTED_WITHIN_SCREEN` does not accept or promote a design.
The next evidence should be a short readable Program Controller probe over the
same required transition. Locked Benchmarks and Development Reviews retain
capability and promotion authority.

## Quadruped finding

The first study,
`examples/quadruped/design-studies/embodiment-first-recovery.design-study.json`,
compares four inherited rigid/waist Assemblies with 2,048 samples per resting
orientation. All four are falsified because their authored home keyframes place
only two of four declared feet within the 3 cm tolerance. The
contact-seeking-waist candidate also exposes a directional rear-recovery
bottleneck: only one collision-free foot reaches tolerance in the
`fallen-back` screen.

This is exactly the intended development-emphasis signal. Fix and re-screen
the nominal plant before spending more RL budget; then use a bounded dynamic
probe to decide whether the remaining recovery failure belongs to geometry or
behavior.
